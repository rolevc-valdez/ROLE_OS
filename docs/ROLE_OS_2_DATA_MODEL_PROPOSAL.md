# Role OS 2.0 Data Model Proposal

Status: proposal only. Describes the minimum data needed to answer ¿Dónde me quedé? / ¿Qué importa ahora? / ¿Qué sigue?, and maps each entity to existing tables/models that can probably be reused as-is. No schema, migration, or data has been changed. All table/field names below are copied from the actual `CREATE TABLE` statements and dataclasses in the current codebase.

## Approach

Do not design a new schema. Six entities are needed: Project, State, Action, Context, Session, Resume Target. Every one of them already has a working, sufficient home in the existing SQLite databases under `dashboard/app/*/db.py` and the dataclasses in `dashboard/app/discovery/models.py`. This document names those homes explicitly and flags the one place a table is genuinely missing a field.

## Entity: Project

**Minimum fields needed:** stable id, display name, filesystem root path, classification/kind, health signal, adoption status.

**Reuse — three existing layers, already correctly separated, no new table needed:**

- `app/discovery/models.py: DiscoveredProject` (in-memory, not a DB table) — the filesystem-observed truth: `root_path`, `name`, `depth`, `git` (`GitInfo`), `classification`, `confidence_score`, `health_score`, `item_id`, `item_kind`, `project_root_id`, `is_top_level_project`. Regenerated by re-scanning; never a store of human decisions.
- `app/workspace/db.py: adopted_projects` — `id`, `root_path` (UNIQUE), `adopted`, `ignored`, `priority`, `business_value`, `status`, `tags` (JSON), `notes` (JSON), `adopted_at`, `created_at`, `updated_at`. The adoption overlay: deliberately does not duplicate Discovery's metadata.
- `app/projects/db.py: projects` — `id`, `workspace_id` (→ `workspaces`), `name`, `description`, `status`, `health_score`, `priority`, `tags`, `owner`, `notes`, `decisions`, `todos`, `deliverables`, `assets`, `prompts` — the canonical, promoted project record. This is the row Resume Work, Project Memory, and Mission Control all key off (`canonical_project_id`).

**Known join gap (do not "fix" with a new table):** these three layers share no single foreign key; they are matched by `root_path` equality or case-insensitive `name` match (confirmed in `project_memory/service.py: _current_objective()`, matching against `app.session.db: registry_projects` by lowercased `project_name`). 2.0 should document this as a permanent, accepted constraint, not invent a fourth id space to "solve" it.

## Entity: State ("¿Dónde me quedé?")

**Minimum fields needed:** last human-authored summary of where things stand, fallback to last commit, timestamp/freshness.

**Reuse:**

- `app/projects/db.py: ai_session_snapshots` — `id`, `session_id` (→ `ai_sessions`), `accomplishments`, `blockers`, `pending_work`, `next_prompt`, `decisions`, `summary`, `created_at`. This is already exactly "state as of last checkpoint," human-authored.
- `app/discovery/models.py: GitInfo` (nested in `DiscoveredProject.git`) — `last_commit_hash`, `last_commit_date`, `last_commit_message`, `recent_commits` (list of `CommitInfo{hash, date, message}`) — the mechanical fallback truth.
- Composition logic already exists and needs no new field: `project_memory/service.py: _where_we_left_off(context, snapshot)` — prefers `snapshot.summary`/`accomplishments`, then `git.last_commit_message` + `git.last_commit_date`, then the honest string `"No prior activity recorded."`.

No new table needed. The only gap: `ai_session_snapshots` has no explicit "as_of"/staleness flag distinct from `created_at` — for 2.0, treat `created_at` as the freshness field and render it whenever a snapshot is shown, rather than adding a column.

## Entity: Action ("¿Qué sigue?")

**Minimum fields needed:** current single-line objective, next concrete action + its source, pending work description.

**Reuse — no dedicated table; this is computed, not stored, which is correct for 2.0 (it should stay derived, not become another place data can go stale):**

- `_current_objective()` (`project_memory/service.py`) — sources, in priority order: `app.session.db: sessions.objective` (matched by project name) → ROADMAP.md's active-phase marker (file read, not DB) → default `"Continue this project"`.
- `_next_action_output()` — sources: `app.discovery.next_action.extract_next_action` (reads NEXT_ACTION.md → TODO.md → ROADMAP.md, attached to `DiscoveredProject`/context, not a table) → Operational Intelligence's `suggested_action` → honest empty.
- `_pending_work()` — sources: `ai_session_snapshots.pending_work` → the same Next Action text (tagged with its source) → the Operational Intelligence recommendation's `recommendation`/`reason`.
- Operational Intelligence and Executive Decision scores (`app/operational_intelligence`, `app/executive_decision`) are deterministic, additive-point-table computations over `DiscoveredProject`/context fields — no dedicated persistent table today, and none is needed; they're cheap to recompute per request via `all_project_contexts()`.

## Entity: Context

**Minimum fields needed:** everything Resume Work needs to write a self-sufficient prompt: display name, root path, classification, technology stack, health, git status, latest activity.

**Reuse:**

- `app/project_context/builder.py: build_project_context()` / `all_project_contexts()` — already the single composer; its return dict (as consumed by `build_project_memory`) carries `display_name`, `root_path`, `classification`, `technology_stack`, `health`, `git`, `latest_activity`, `latest_ai_session`, `next_action`, `latest_snapshot`. No new entity needed — Context is a computed view over Project + State + Action, not separate storage.
- The Context Sufficiency Guard's inputs (embedded resource/character counts) are computed at prompt-build time (`app.project_memory.session_intent`), not stored — correct as-is; storing them would let them go stale independent of the filesystem they describe.

## Entity: Session

**Minimum fields needed:** which conversation/tool this project's work is happening in, and where to find it again.

**Reuse:**

- `app/projects/db.py: ai_sessions` — `id`, `project_id` (→ `projects`), `title`, `assistant`, `conversation_url`, `role`, `preferred_model`, `started_at`, `last_used_at`, `status`, `favorite`, `current`, `notes`. This is the canonical Session entity — one row per (project, assistant conversation).
- Legacy/parallel: `app/session/db.py: sessions` (Daily Session, v1.0) — `id`, `date`, `project_id` (→ its own `registry_projects`, not canonical `projects`), `project_name`, `mode`, `objective`, `expected_result`, `notes`, `status`, `completed_work`, `decisions`, `blockers`, `next_step`. Still feeds `current_objective` today via name-matching; kept as a supporting input, not promoted to the canonical Session entity.

No new table needed for canonical Session; `ai_sessions` + `ai_session_snapshots` together already are Session + State-checkpoint-of-that-session.

## Entity: Resume Target

**Minimum fields needed:** which assistant/environment to open, why, and the working directory if local execution is required.

**Reuse — computed, not stored (correctly, since it must always reflect the project's current classification/git/tech-stack, not a snapshot of a past decision):**

- `app/workspace/execution_target.py: classify_execution_target()` returns `{execution_target, reason, working_directory, recommended_assistant, available_assistants}` from `root_path`, `classification`, `git_is_repo`, `requested_action`, `technology_stack` — all already present on Context. Values: `claude_code` / `claude_web` / `chatgpt_web` / `user_choice` (constants `CLAUDE_CODE`, `CLAUDE_WEB`, `CHATGPT_WEB`, `USER_CHOICE` in the same module).
- `app/workspace/resume.py: resume_work()`'s return shape is effectively the full Resume Target payload already: `session_id`, `is_new_session`, `prompt`, `url`, `used_saved_conversation`, `execution_target`, `execution_target_reason`, `working_directory`, `recommended_assistant`, `available_assistants`. No new table needed; this is exactly the entity the "CONTINUAR TRABAJANDO" button needs, already assembled.

## Summary Table

| Entity | Existing home(s) | New storage needed? |
|---|---|---|
| Project | `DiscoveredProject` (in-memory) + `adopted_projects` + `projects` | No |
| State | `ai_session_snapshots` + `GitInfo`/`recent_commits` | No |
| Action | Computed in `project_memory/service.py` from `next_action` (file-derived), `sessions.objective`, Operational Intelligence | No |
| Context | `build_project_context()` / `all_project_contexts()` composed view | No |
| Session | `ai_sessions` (canonical) / `session.db: sessions` (legacy input) | No |
| Resume Target | `classify_execution_target()` + `resume_work()` return shape | No |

## Explicit Non-Recommendation

This document deliberately does not propose any new table, column, or id scheme. The one real structural issue — three unlinked project-identity spaces (Discovery `item_id`, `adopted_projects.id`, canonical `projects.id`, plus Daily Session's separately-keyed `registry_projects`) — should be treated as a documented, permanent constraint for Role OS 2.0, not patched with a new join table, per the reasoning in `ROLE_OS_2_ARCHITECTURE_PROPOSAL.md`'s "Components That Need Simplification" section.
